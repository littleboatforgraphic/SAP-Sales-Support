# UI Specifications
## AI Agent System for Office Admin & Sales Workflow — Wire Mesh Manufacturing

**Status:** Draft for review
**Version:** 0.1

---

## 1. Interaction Channels

| Channel | Used for |
|---|---|
| **WhatsApp (coexistence number)** | All salesperson-agent interaction; admin's live/manual participation via the WhatsApp Business app on the same number |
| **Email (incoming)** | Customer POs received via email (read-only monitoring via IMAP/POP3); agents detect and process PO attachments automatically |
| **Email (outgoing)** | Delivery of SO/invoice/quotation documents to the customer (with CC list), primarily for e-invoice documentation; agents do not send conversational emails to customers |

There is no separate graphical app for salespeople or customers in v1 — the entire customer-facing and salesperson-facing experience is conversational, through WhatsApp. An optional lightweight admin interface (glossary/price-table maintenance) is described in Section 6 as a future nice-to-have.

## 2. Trigger Design

Two ways a message reaches the agent:

1. **Explicit prefix** — salesperson starts the message with `AI`, `Agent`, or `AI agent`. Always routes to the agent.
2. **Keyword fallback** — if no prefix is used, the agent scans for business-intent keywords (e.g. "Order", "New Acc", "Quotation", "Invoice", "Payment", and their Malay/shortform equivalents from the glossary). Keyword matching should be reasonably specific to avoid false positives on ordinary conversation (e.g. avoid triggering on the bare word "order" alone if that risks matching casual chat).

If neither is present, the message is not processed by the agent at all — it remains a normal WhatsApp conversation between admin and salesperson.

## 3. Acknowledgement Messages

Fired immediately on trigger detection, before the full draft is ready — this prevents the salesperson wondering whether the message registered, and gives an early, cheap check on whether the agent understood correctly.

**Explicit-prefix acknowledgement** (intent was deliberate — acknowledgement can be brief):
> "Got it — checking stock for [product/spec] now."

**Keyword-fallback acknowledgement** (intent was inferred — acknowledgement should say so, and offer an easy correction):
> "Noticed this looks like a new order — drafting it now. Let me know if that's not what you meant."

## 4. Confirmation-Echo Pattern

Before finalizing anything with financial or contractual weight, the agent restates what it understood, in plain structured language, and waits for explicit confirmation.

**Quote confirmation:**
> "Confirming: [quantity] units of [spec/SKU], RM[price]/unit, based on current pricing. Reply YES to send this to the customer, or tell me what to change."

**Order/PO confirmation (including PO-extracted orders):**
> "From the PO: [items, quantities, prices, delivery terms]. Note: PO price differs from current price table — please confirm which price applies."

**Address validation - Trading house (new address detected):**
> "PO delivery address differs from registered addresses. Customer is a trading house — proceeding with caution. Please double-confirm delivery address is correct before proceeding."

**Address validation - Non-trading house (new address detected):**
> "PO delivery address differs from registered addresses. Customer is NOT a trading house — this is flagged as high-risk. Admin approval required before proceeding with this order."

**Non-PO order confirmation:**
> "No PO received. Generated sales order [SO number] for customer confirmation. Please have customer sign and return before we proceed with Delivery Order and invoicing."

**Low-confidence / unresolved term:**
> "Couldn't match '[term]' to a product in our system. Did you mean [SKU A], [SKU B], or [SKU C]?"

**Payment entry draft (sent to accountant, not auto-confirmed):**
> "Drafted a payment entry from the file forwarded: RM[amount], [date], ref [reference]. Please reconcile against bank records and confirm before this is finalized in SAP."

## 5. Document Delivery Messages

**To salesperson (WhatsApp):**
> "[Document type] for [customer/order ref] is ready — attached." *(SO/invoice/quotation PDF attached, generated by SAP)*

**To customer (email):**
- Subject: e.g. `Invoice [number] — [Company Name]`
- Body: short, professional, references the order/reference number.
- Recipients: customer-provided email address + CC list as supplied by the customer for that transaction.

## 6. Admin-Facing Interaction

Since the design uses **WhatsApp coexistence** rather than a separate inbox tool:

- The admin sees the live conversation in their own WhatsApp Business app on the shared number, and can type manually at any time.
- When the admin manually replies within a conversation, the agent should detect this (via the synced outgoing message) and stand down from that conversation for a defined window, to avoid duplicate or conflicting replies.
- Drafts requiring approval (order-to-invoice, customer onboarding) are posted into the same shared thread, visible to both the salesperson and the admin — since coexistence gives the admin live visibility, a separate private relay channel is not the default for these approvals, though the underlying agent logic should be built so a private relay/dashboard could be reintroduced later without a redesign.

### 6.1 Future consideration — admin maintenance interface
Not required for v1, but noted as a natural next step once the glossary and price table are in active use: a simple internal web page (or shared spreadsheet, at minimum) where the admin can:
- View and edit the price reference table.
- Approve or reject pending glossary entries (new shortform-to-SKU mappings the agent has proposed).
- View the daily/weekly token usage and cost summary.

This does not need to be built for the initial phases — a shared spreadsheet is an acceptable substitute until agent volume justifies a dedicated interface.

## 7. Language & Tone Guidelines

- Agent messages should default to the same language mix the salesperson used (English, Malay, or a mix) rather than forcing a single language.
- Keep confirmation and acknowledgement messages short and structured — avoid long paragraphs in a WhatsApp thread.
- Never let an ambiguous shortform silently resolve without either a glossary hit or a clarifying question — this is a hard rule, not a style preference.

## 8. Error / Exception States

| Situation | Agent behavior |
|---|---|
| Stock shortfall | Escalate to admin; salesperson informed a check is in progress |
| Non-standard spec | Escalate to admin |
| Unresolved SKU/term | Ask salesperson to clarify from top candidates; escalate to admin if still unresolved |
| PO price ≠ current price table | Flag explicitly, do not silently pick one |
| PO delivery address ≠ registered (trading house) | Flag with caution message; proceed with admin double-confirmation |
| PO delivery address ≠ registered (non-trading house) | Flag as high-risk; escalate to admin for fraud prevention before proceeding |
| Order without PO | Generate SAP sales order for customer signature; do not proceed with DO/invoicing until signed order returned |
| Possible duplicate customer (onboarding) | Flag to admin before drafting the new account |
| Scanned/low-quality PDF | Treated with extra caution — always requires admin confirmation, never auto-trusted |
| Payment PDF received | Agent drafts the SAP entry only; never confirms/clears a payment — accountant must reconcile against bank records first |
